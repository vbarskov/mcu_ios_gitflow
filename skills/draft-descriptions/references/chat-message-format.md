# Сообщения для командного чата

Нормативный источник — [«Требования процесса разработки», IVA Wiki](https://wiki.iva.ru/spaces/IVCS/pages/72588399/), проверен 3 ноября 2026 года. Сообщения оформляются по Wiki с уточнением пользователя об учёте тестов в технических строках и записи сокращения «т.» с точкой. Сообщение для чата отличается от содержимого описания MR.

УЗС — три строки:

```text
Сливаю УЗС-[номер в серии]: [название задачи в инфинитиве]
[ссылка на УЗС]
√[всего добавлено строк], 💀, [целевая ветка], >=2, тест ([длительность] сек)
```

Если целевая ветка УЗС — `minor/...`, сразу после `💀` добавляется `🐥` без пробела между маркерами: `💀🐥`. При реальной демонстрации результата последняя строка заканчивается `, демо`.

КЗС в release или другое назначение, не являющееся ГЗС, — две строки:

```text
КЗС [ссылка на КЗС]
√[всего добавлено строк], [целевая ветка] >= 2, [демо или без демо]
```

КЗС в ГЗС — две строки:

```text
🐬 КЗС в [целевая ветка]: [ссылка на КЗС]
√[всего добавлено строк], [целевая ветка] >= 2, тест ([длительность] сек), [демо или без демо]
```

В сообщении КЗС `🐬` ставится только в первой строке. Во второй строке после `√` дельфин не ставится ни при каком назначении. Для `release` и `release/...` он запрещён и в первой строке. Для других веток формат ГЗС применяется только при явном `kzsTargetIsGzs: true`. Разовый boolean аргумента инструмента отражает ответ автора из текущей беседы и имеет приоритет над сохранённым boolean карточки, не меняя её. `false` означает обычный КЗС. Если оба значения отсутствуют, нужно спросить автора, является ли назначение ГЗС. Имя ветки, включая `giant`, и дельфин в старом заголовке MR не заменяют подтверждения. Само имя `minor/...` тоже не определяет ответ. Во всех вариантах пишется реальная целевая ветка MR, а не ветка из примера Wiki. В любом варианте КЗС последняя строка обязательно содержит `, демо` при реальной демонстрации результата либо `, без демо` при подтверждённом отсутствии. Если данных недостаточно, выводится `, демо [не указано]` и поле `demo` в `missingData`.

При неизвестном статусе ГЗС инструмент возвращает `text: null`, `needsInput: true`, вопрос `question` и `missingData: ["kzsTargetIsGzs"]` до чтения diff. Сначала задай этот вопрос и дождись ответа, затем повтори вызов с `kzsTargetIsGzs: true` или `false`. Если неизвестно назначение, сначала уточни ветку. Не выдавай вопрос за готовый текст для командного чата. Для сообщений УЗС такие вопросы не задаются.

Номер УЗС — номер его части в серии из MR, его заголовка или карточки; это не GitLab IID. В первой строке используй название задачи в инфинитиве из заголовка выбранного MR либо подходящее `task.title`. Очисти его от `!iid`, `#Jira`, маркеров `🐥версия`/`💀`/`🐬`, известного `featureName`, `reopened`, `№части` и итога после точки. Не бери первую строку из `done`, `result` или описания выполненного изменения. Если названия нет, оставь `[название задачи в инфинитиве]`, а не переделывай итог в догадку о названии.

`√` — все добавленные строки полного diff именно этого MR, включая технические строки и тесты. Это не число файлов и не сумма всей серии. У КЗС с пустыми коммитами число может быть 0; при недоступном или неполном diff оно неизвестно, а не 0.

Если общее число добавленных строк **больше 500**, сразу после него обязателен блок `(т. N)`, например структурно `√[всего] (т. [технических]), …`. `N` — фактическое число технических добавленных строк: сгенерированный код, комментарии, пробелы и, по явному указанию пользователя, тесты. Не учитывай одну строку дважды при пересечении категорий. Если всего не больше 500 строк, блок `(т. N)` необязателен по правилам и форматтер его не показывает. При известном общем числе больше 500, но неизвестном техническом числе, оставь в этом блоке пометку и сообщи об этом после сообщения. Если общее число неизвестно, оставь пометку после `√` без догадки о необходимости технического блока. В ответе инструмента `lineCounts` содержит `total`, `technical`, `ordinary`; неизвестные значения равны `null`.

При первичной подаче допускается до 500 нормальных строк и до 10000 технических; нормальные строки — общее число минус технические. При исправлении замечаний ревью превышение допускается. Не выдавай случайный или неполный подсчёт за подтверждение этих ограничений.

Счётчик использует принятую в MCU классификацию: обычные исходники — `.swift`, `.yml` и `.yaml`; остальные файлы относятся к техническим. Отдельно распознаются признак GitLab `generated_file`, каталоги Generated, файлы `*.Generated.swift`/`*.SectionGenerated.swift` и тестовые пути. В обычных исходниках техническими считаются пустые и целиком комментирующие строки; код с комментарием в конце остаётся обычной строкой. При отсутствии пути классификация неизвестна. Незавершённый или недоступный diff не подменяется нулём.

Порог коммитов всегда записывается `>=2` для УЗС и `>= 2` для КЗС. Время UI-теста указывают в секундах только при подтверждённой длительности. Если тест не запускался, напиши `тест (не запускался)`; если сведений нет, оставь `[длительность]`. Во всех форматах с тестом после слова `тест` стоит пробел перед скобкой. В КЗС не в ГЗС поле теста не добавляется. Длительность pipeline и случайное число из старого генератора бота не являются результатом проверки.

`демо` подтверждается реальным материалом результата (`after`/`afterUrl`) либо медиа «Стало» в описании привязанного MR. Снимки кода, текстовое пояснение и пустой раздел демонстрацией не считаются. Для КЗС отсутствие явно обозначается `без демо`; для УЗС суффикс `демо` добавляется только при наличии материала.

Неизвестные значения в квадратных скобках — места для заполнения. Отсутствующая ссылка не означает поручение создать MR. Сам текст сообщения не отправляется коллегам и не выполняет слияние.
