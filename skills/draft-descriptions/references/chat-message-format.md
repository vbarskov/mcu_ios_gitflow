# Сообщения для командного чата

Нормативный источник — [«Требования процесса разработки», IVA Wiki](https://wiki.iva.ru/spaces/IVCS/pages/72588399/), проверен 3 ноября 2026 года. Сообщения оформляются по Wiki с уточнениями пользователя о формате КЗС в ГЗС, учёте тестов в технических строках и записи сокращения «т.» с точкой. Сообщение для чата отличается от содержимого описания MR.

УЗС — три строки:

```text
Сливаю УЗС-[номер в серии]: [название задачи в инфинитиве]
[ссылка на УЗС]
√[всего добавлено строк], 💀, [целевая ветка], >=2, тест ([длительность] сек)
```

Если целевая ветка УЗС — `minor/...`, сразу после `💀` добавляется `🐥` без пробела между маркерами: `💀🐥`. При реальной демонстрации результата последняя строка заканчивается `, демо`.

КЗС в release или другое назначение, не являющееся ГЗС, — две строки:

```text
КЗС: [ссылка на КЗС]
√[всего добавлено строк], [целевая ветка] >= 2, [демо или без демо]
```

КЗС в ГЗС состоит из двух строк. В первой указывается фактическая ветка назначения КЗС. Во второй `release >= 2` — фиксированный текст шаблона, за которым сразу следует состояние демонстрации.

```text
🐬 КЗС в [целевая ветка]: [ссылка на КЗС]
√[всего добавлено строк], release >= 2, [демо или без демо]
```

Пример КЗС в ГЗС с демонстрацией.

```text
🐬 КЗС в feature/taskNumber-featureName: https://git.hi-tech.org/mobile/apple/messenger/-/merge_requests/xxxx
√xxx, release >= 2, демо
```

Сам ГЗС — отдельное сообщение из трёх строк, предусмотренное Wiki:

```text
Сливаю ГЗС: [собственное название ГЗС в инфинитиве]
[ссылка на сам ГЗС]
√[всего добавлено строк], 🐬, [фактический target_branch ГЗС] >= 2, тест ([длительность] сек), [демо или без демо]
```

Это сообщение о реализации фичи в родительском MR. В нём `🐬` обязателен именно в третьей строке после `√`, включая назначение `release`/`release/...`. Запрет дельфина после `√` и для release ниже относится только к сообщению **КЗС**, а не самого ГЗС. При общем числе больше 500 после числа добавляется ` (т. N)` по правилам подсчёта ниже.

Для ГЗС вызывайте `mcu_chat_message` с `{taskId, kind: "gzs", iid?, testSeconds?}`. MR заново читается по явному `iid` или `task.gzs.iid`; если оба отсутствуют, сначала спросите номер или ссылку ГЗС. Это чтение не выполняет привязку и не меняет карточку. Название, URL, целевая ветка, diff и медиа берутся исключительно из самого ГЗС. `task.title`, номера, результаты, diff и демонстрация дочерних УЗС/КЗС не заменяют его данные. Для первой строки очистите собственный заголовок ГЗС от префикса `!MR`, всех префиксов Jira, маркеров и служебного окончания «Гигант». Исходный заголовок и весь набор Jira сохраняются в данных; основная Jira по порядку не выбирается.

Для теста ГЗС допустима только подтверждённая длительность его UI-теста. Если известно, что он не запускался, пишется `тест (не запускался)`, при неизвестности — `тест ([длительность] сек)`. Последняя строка всегда завершается `демо`, `без демо` или `демо [не указано]` по материалам самого ГЗС. Наличие теста или видео у дочернего запроса этого не подтверждает. В ГЗС учитываются собственные материалы результата с подписями «Стало», «Демо», «Демонстрация» или «Результат», а также материалы в разделе демонстрации. Код и материалы «Было» не подтверждают итог. При неоднозначном медиа остаётся `демо [не указано]`; примеры разметки в коде и комментариях не считаются демонстрацией. `mcu_attach_gzs`, создание MR, публикация, слияние и действия в Jira ради этого текста не выполняются.

В сообщении КЗС `🐬` ставится только в первой строке. Во второй строке после `√` дельфин не ставится ни при каком назначении. Для `release` и `release/...` он запрещён и в первой строке. Для других веток формат «КЗС в ГЗС» применяется только при явном `kzsTargetIsGzs: true`. Разовый boolean аргумента инструмента отражает ответ автора из текущей беседы и имеет приоритет над сохранённым boolean карточки, не меняя её. `false` означает обычный КЗС. Если оба значения отсутствуют, нужно спросить автора, является ли назначение ГЗС. Имя ветки, включая `giant`, и дельфин в старом заголовке MR не заменяют подтверждения. Само имя `minor/...` тоже не определяет ответ. В любом варианте КЗС последняя строка обязательно содержит `, демо` при реальной демонстрации результата либо `, без демо` при подтверждённом отсутствии. Если данных недостаточно, выводится `, демо [не указано]` и поле `demo` в `missingData`.

Для сообщения КЗС при неизвестном статусе его назначения инструмент возвращает `text: null`, `needsInput: true`, вопрос `question` и `missingData: ["kzsTargetIsGzs"]` до чтения diff. Сначала задай этот вопрос и дождись ответа, затем повтори вызов с `kzsTargetIsGzs: true` или `false`. Если неизвестно назначение, сначала уточни ветку. Не выдавай вопрос за готовый текст для командного чата. Для сообщений УЗС и самого ГЗС вопрос о `kzsTargetIsGzs` не задаётся.

Явный контекст автора о направлении КЗС в существующий родительский ГЗС достаточен; повторное подтверждение и привязка ради текста не нужны. У родительского ГЗС могут быть собственное название и несколько Jira: сохраняйте их целиком отдельно, не заменяйте данными текущего запроса и не назначайте первую Jira основной автоматически. Текущие сообщения ссылаются на соответствующий УЗС/КЗС. `mcu_attach_gzs` сохраняет локальную связь для Git Flow, поэтому при простом запросе сообщения его не вызывают.

Номер УЗС — номер его части в серии из MR, его заголовка или карточки; это не GitLab IID. В первой строке используй название задачи в инфинитиве из заголовка выбранного MR либо подходящее `task.title`. Очисти его от `!iid`, `#Jira`, маркеров `🐥версия`/`💀`/`🐬`, известного `featureName`, `reopened`, `№части` и итога после точки. Не бери первую строку из `done`, `result` или описания выполненного изменения. Если названия нет, оставь `[название задачи в инфинитиве]`, а не переделывай итог в догадку о названии.

`√` — все добавленные строки полного diff именно этого MR, включая технические строки и тесты. Это не число файлов и не сумма всей серии. У КЗС с пустыми коммитами число может быть 0; при недоступном или неполном diff оно неизвестно, а не 0.

Если общее число добавленных строк **больше 500**, сразу после него обязателен блок `(т. N)`, например структурно `√[всего] (т. [технических]), …`. `N` — фактическое число технических добавленных строк: сгенерированный код, комментарии, пробелы и, по явному указанию пользователя, тесты. Не учитывай одну строку дважды при пересечении категорий. Если всего не больше 500 строк, блок `(т. N)` необязателен по правилам и форматтер его не показывает. При известном общем числе больше 500, но неизвестном техническом числе, оставь в этом блоке пометку и сообщи об этом после сообщения. Если общее число неизвестно, оставь пометку после `√` без догадки о необходимости технического блока. В ответе инструмента `lineCounts` содержит `total`, `technical`, `ordinary`; неизвестные значения равны `null`.

При первичной подаче УЗС допускается до 500 нормальных строк и до 10000 технических; нормальные строки — общее число минус технические. Лимит объёма относится к УЗС. При исправлении замечаний ревью превышение допускается. Не выдавай случайный или неполный подсчёт за подтверждение этих ограничений.

Счётчик использует принятую в MCU классификацию: обычные исходники — `.swift`, `.yml` и `.yaml`; остальные файлы относятся к техническим. Отдельно распознаются признак GitLab `generated_file`, каталоги Generated, файлы `*.Generated.swift`/`*.SectionGenerated.swift` и тестовые пути. В обычных исходниках техническими считаются пустые и целиком комментирующие строки; код с комментарием в конце остаётся обычной строкой. При отсутствии пути классификация неизвестна. Незавершённый или недоступный diff не подменяется нулём.

Порог коммитов всегда записывается `>=2` для УЗС и `>= 2` для КЗС и ГЗС. Поле UI-теста используется только в УЗС и ГЗС. Подтверждённую длительность указывают в секундах. Если тест не запускался, напиши `тест (не запускался)`. Если сведений нет, оставь `[длительность]`. После слова `тест` ставится пробел перед скобкой. Длительность pipeline и случайное число из старого генератора бота не являются результатом проверки.

`демо` подтверждается реальным материалом результата (`after`/`afterUrl`) либо медиа «Стало» в описании соответствующего MR. Снимки кода, текстовое пояснение и пустой раздел демонстрацией не считаются. Для КЗС и ГЗС отсутствие явно обозначается `без демо`; для УЗС суффикс `демо` добавляется только при наличии материала. Материалы одного MR не переносятся в сообщение другого.

Неизвестные значения в квадратных скобках — места для заполнения. Отсутствующая ссылка не означает поручение создать MR. Сам текст сообщения не отправляется коллегам и не выполняет слияние.
