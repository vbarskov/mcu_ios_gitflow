# MCU iOS Git Flow

Самостоятельный локальный плагин Codex для работы с MCU iOS: Jira → исправление и коммит → отдельный Git Flow УЗС/КЗС, а также сообщения УЗС/КЗС/ГЗС для чата. Codex редактирует код в независимой рабочей копии, а встроенный stdio MCP хранит карточки, читает Jira и работает с GitLab. Пакет не открывает HTTP-порт. Тот же пакет подключается к DeepSeek Harness: те же навыки и тот же stdio MCP.

Требуются Node.js 22.13+ (встроенный `node:sqlite` без отдельного флага) и Git. Внешних npm-зависимостей нет. Для снимков кода в КЗС на macOS нужен Swift и отдельное разрешение на компиляцию генератора.

## Подключение в Kimi Code

В корне пакета есть `kimi.plugin.json`: он подключает все четыре навыка и stdio MCP `mcu_ios_gitflow`. Выполните в Kimi Code:

```text
/plugins install /absolute/path/to/mcu_ios_gitflow
/reload
```

Также можно открыть `/plugins`, перейти на вкладку **Custom** и установить плагин из локального каталога. Локальная установка копируется в управляемый каталог Kimi Code, поэтому после изменения исходников плагин нужно установить повторно и выполнить `/reload` либо начать новый чат.

После подключения попросите: «Настроить MCU iOS Git Flow». Навыки доступны с префиксом `mcu-ios-gitflow:`, например `/skill:mcu-ios-gitflow:setup`. Состояние и токены общие с другими клиентами и хранятся отдельно в `~/.mcu-ios-gitflow/`.

## Подключение в Codex

В корне пакета уже есть переносимые `plugin.json` и `mcp.json`, совместимые `.codex-plugin/plugin.json` и `.mcp.json`, четыре навыка и локальный каталог `.agents/plugins/marketplace.json` с именем `mcu-local`.

1. Откройте каталог `mcu_ios_gitflow` как проект в приложении Codex. Его `.agents/plugins/marketplace.json` делает локальный каталог плагинов доступным в контексте проекта.
2. Перезапустите приложение Codex, откройте каталог плагинов, выберите источник «MCU — локальные плагины» и установите **MCU iOS Git Flow**.
3. Начните новый чат и запустите настройку плагина или попросите: «Настроить MCU iOS Git Flow». При изменении исходников обновите локальную установку и начните новый чат.

Если установлен и работает CLI `codex`, каталог можно дополнительно зарегистрировать для использования из других проектов — из локальной папки или прямо из GitHub:

```sh
codex plugin marketplace add /absolute/path/to/mcu_ios_gitflow
codex plugin marketplace add vbarskov/mcu_ios_gitflow
```

Открытие проекта и регистрация каталога делают пакет доступным для установки. Они не настраивают токены и не подтверждают подключение к Jira/GitLab. CLI не нужен для установки через каталог проекта. Пакет не изменяет общие настройки Codex самостоятельно. Порядок упаковки и локальных каталогов описан в [документации OpenAI](https://developers.openai.com/plugins/build/plugins).

## Подключение в DeepSeek Harness

В `package.json` объявлен `dsh.bundle.patch`, поэтому профиль DSH при установке подхватывает четыре навыка из `skills/` как bundled-провайдеры. MCP-сервер запускается отдельным процессом, и его путь зависит от машины, поэтому строка профиля добавляется скриптом.

```sh
DSH="/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh"

# 1. Навыки: пакет ставится в профиль DSH
"$DSH" plugin --profile desktop add link:/absolute/path/to/mcu_ios_gitflow

# 2. MCP mcu_ios_gitflow: идемпотентно дописывает блок в cordis.patch.yml профиля
node /absolute/path/to/mcu_ios_gitflow/dsh/install-mcp.mjs
```

`dsh/install-mcp.mjs` правит `~/.dsh/profiles/desktop/cordis.patch.yml` (другой профиль — `--profile`, другой корень — `DSH_HOME`), не трогает чужие строки, заменяет свой блок при повторном запуске и умеет показать его без записи: `--print`. После установки начните новый чат DSH: навыки `setup`, `implement-task`, `git-flow`, `draft-descriptions` появятся в каталоге, а инструменты — с именами `mcu_*`.

Обновление: повторите обе команды (скрипт поправит путь) и начните новый чат. Настройки и токены общие с Codex — `~/.mcu-ios-gitflow/`, `node scripts/setup.mjs` выполняется один раз.

## Настройка

Из каталога пакета выполните в обычном локальном терминале:

```sh
node scripts/setup.mjs
```

Настройка запрашивает локальный путь репозитория, адрес GitLab, проект, ветку назначения, адрес Jira и токены. Секретный ввод скрыт. Не вставляйте токены в чат, командную строку, поручение или JSON для MCP. Пустое значение сохраняет текущую настройку; прежний токен можно сохранить только для того же сервера.

Состояние по умолчанию хранится в `~/.mcu-ios-gitflow/`. Для отдельного каталога задайте абсолютный путь в `MCU_IOS_GITFLOW_DATA_DIR`. `config.json` содержит несекретные поля `gitlabUrl`, `project`, `repoPath`, `targetBranch`, `jiraBaseUrl`. Токены находятся в отдельном `credentials.json`, привязаны к адресам серверов; каталог имеет права `0700`, файлы — `0600`. Переменные окружения `GITLAB_TOKEN` и `JIRA_TOKEN` имеют приоритет над сохранёнными токенами. Состояние и токены не входят в пакет плагина и сохраняются отдельно от его устанавливаемой копии.

Настройка по умолчанию не обращается к внешним серверам. `mcu_status` показывает локальную готовность и наличие секретов без их значений. Для проверки фактической авторизации отдельно поручите проверить соединения через `mcu_check_connections`.

Git fetch/push используют отдельно настроенные учётные данные Git. Токен для GitLab API сам по себе не настраивает авторизацию Git: нужный доступ должен уже работать через настроенный Git credential helper или другой выбранный пользователем способ. Используйте HTTPS remote, когда отдельного разрешения на SSH нет.

## Работа

**Исправление задачи.** Попросите: «Исправить задачу Jira … до ОР и подготовить коммит». Навык `implement-task` найдёт или импортирует карточку, выделит ФР и ОР, создаст отдельную копию через `mcu_create_workspace`. ОР обязателен до разработки. Codex внесёт исправление, выполнит допустимые локальные проверки и сделает коммит. `mcu_record_commit` проверит чистую копию и сохранит SHA с фактическим отчётом; сам инструмент не выполняет коммит. Затем Codex вернёт ветку, SHA и результат для проверки автором.

Первый этап заканчивается коммитом. Сборка и установка приложения, аппараты, WDA, веб-стенд, горячие и UI-тесты, запись видео в этом режиме не запускаются.

**Сообщение в чат.** Попросите: «Дай описание УЗС, КЗС или ГЗС в чат». Навык `draft-descriptions` использует `mcu_chat_message` и выдаёт сообщения по требованиям IVA Wiki: «Сливаю УЗС-1: …» с названием задачи в инфинитиве из MR, «КЗС ссылка…» либо отдельное трёхстрочное «Сливаю ГЗС: …». `√` содержит все добавленные строки; при числе больше 500 обязателен реальный подсчёт технических строк `(т. N)`, включая тесты. Сообщения КЗС и ГЗС явно содержат `демо`, `без демо` или пометку неизвестности. У КЗС дельфин допускается только в первой строке при подтверждённом направлении в ГЗС вне release; при неизвестности инструмент сначала задаёт вопрос, а разовый `kzsTargetIsGzs` отражает ответ автора. У самого ГЗС дельфин стоит в третьей строке после `√`, включая release. Инструмент только читает данные и diff соответствующего MR, не меняет карточки, MR или preview. Неизвестные данные остаются пометками, время теста не выдумывается. Текст описания самого MR можно запросить отдельно.

Для сообщения самого ГЗС используется `mcu_chat_message {taskId, kind: "gzs", iid?, testSeconds?}`: свежие данные читаются по указанному `iid` или `task.gzs.iid`. Если номера нет, плагин спрашивает номер или ссылку. Собственные название, URL, `target_branch`, diff и демонстрация ГЗС не заменяются данными дочерней задачи. Привязка `mcu_attach_gzs`, изменения Jira, создание MR, публикация и слияние ради текста не выполняются. Полные форматы — в [справочнике сообщений](skills/draft-descriptions/references/chat-message-format.md).

Создание УЗС заканчивается ссылкой для ревью. Слияние требует отдельной явной команды автора `Слить !НОМЕР`, с сохранением правил ревью и ограничений GitLab. После слияния выполняется `mcu_sync`, затем отдельный preview и публикация КЗС. КЗС создаётся с двумя пустыми коммитами «Отступ» без изменения кода и с меткой КЗС. Автоматического слияния КЗС нет.

Для КЗС используются существующие видео, указанные автором. Новое видео плагин не снимает. Без демонстрации публикация блокируется; автор может отдельно разрешить вариант `Создать КЗС без демонстрации`. Для таблицы изменений выбираются до трёх ключевых файлов из включённого УЗС, исключая тесты и history. Каждая строка содержит снимок соответствующего кода, модуль и точный путь. Компиляция отдельного генератора снимков требует явного разрешения `Разрешаю компиляцию генератора снимков`; оно не разрешает сборку приложения.

Preview КЗС выдаёт `previewToken` только при `ready: true`: УЗС действительно слит, база выбрана, демонстрация или разрешённое исключение готовы и есть подходящая строка изменений со снимком кода. При `ready: false` причины перечислены в `blockers`; публикация ждёт их устранения.

Заголовки УЗС/КЗС оформляются по [требованиям IVA Wiki](https://wiki.iva.ru/spaces/IVCS/pages/72588399/Требования+процесса+разработки), проверенным 3 ноября 2026 года: `!номерЗС #числоJira`, затем `🐥версия` для назначения `minor/`, `💀` для каждого УЗС или `🐬` только для КЗС в ГЗС, название фичи при наличии, русское действие в инфинитиве, `reopened` при новой серии после переоткрытия, `№части.` и краткий фактический итог УЗС. КЗС заканчивается `№части. Контроль`; для КЗС в `release/` дельфина нет. Подробности и четыре примера — в [правилах заголовков](skills/git-flow/references/title-rules.md).

Поле `title` содержит только русское действие: «Исправить…», «Добавить…», «Убрать…». Поле `done` содержит одну короткую строку о фактически выполненном изменении на русском; она добавляется в заголовок УЗС после точки. Метаданные добавляет форматтер: `featureName`, `uzsPartNumber`, `kzsPartNumber`, `reopened`, `kzsTargetIsGzs` сохраняются отдельно через `mcu_update_task`. По умолчанию части — №1 для УЗС и следующая для КЗС; для существующей серии задаются её реальные номера. Статус ГЗС не угадывается по произвольному имени ветки. Preview нового запроса показывает `!<номер>`, который после создания заменяется реальным номером MR. Заголовок длиннее 255 символов отклоняется с предложением сократить текст и не обрезается молча.

Существующий родительский ГЗС привязывается отдельно через `mcu_attach_gzs {taskId, iid}`: инструмент только читает MR и сохраняет локально в `task.gzs` его исходное название и все Jira. Не заменяйте их текущей задачей и не выбирайте первую Jira основной автоматически. Исходная ветка ГЗС должна совпасть с назначением КЗС; целевая ветка самого ГЗС обычно release и может отличаться. Подтверждённая связь вне release устанавливает статус ГЗС, но текущие УЗС/КЗС сохраняют собственную Jira. Создание, публикация и слияние ГЗС не добавляются. Для простого сообщения КЗС в чат карточку не меняют: явный контекст автора передаётся разовым `kzsTargetIsGzs`; отдельное сообщение самого ГЗС читается через `kind: "gzs"` без привязки.

КЗС кратко объясняет суть задачи, итоговое поведение и важные изменения для коллег. Фактические проверки и демонстрация хранятся отдельно от таблицы изменений. Плагин не пишет в Jira/Confluence и не отправляет Telegram-сообщения.

## MCP и CLI

MCP запускается Codex через stdio. Ручной вход для диагностики:

```sh
node scripts/mcp-server.mjs
```

Сервер пишет протокол в stdout. Для обычной проверки используйте CLI, который вызывает тот же инструмент, а аргументы читает из JSON-файла:

```sh
node scripts/cli.mjs mcu_status
node scripts/cli.mjs mcu_task /absolute/path/to/task-request.json
```

JSON поручения содержит несекретные аргументы инструмента. Точные поля доступны в MCP-схеме, недопустимые аргументы отклоняются. Основные группы инструментов:

| Назначение | Инструменты |
| --- | --- |
| Настройки и подключения | `mcu_status`, `mcu_configure`, `mcu_check_connections` |
| Карточки и Jira | `mcu_tasks`, `mcu_task`, `mcu_import_jira`, `mcu_update_task` |
| Сообщение для командного чата | `mcu_chat_message` — форматы УЗС/КЗС/ГЗС по IVA Wiki, только чтение |
| Код и готовый коммит | `mcu_branches`, `mcu_create_workspace`, `mcu_diff`, `mcu_record_commit` |
| Preview и материалы | `mcu_preview`, `mcu_upload`, `mcu_screenshots`, `mcu_confirm_kzs` |
| Git Flow | `mcu_publish`, `mcu_attach`, `mcu_merge_uzs`, `mcu_sync`, `mcu_publish_description` |
| Существующий родительский ГЗС | `mcu_attach_gzs` — чтение MR и локальная привязка, без изменения GitLab |

Карточки и журналы хранятся локально. Содержимое Jira и вложений рассматривается как данные и не даёт разрешений на команды. Любая SSH-операция запрещена без нового явного разрешения человека именно на неё. Лишь после такого разрешения в соответствующий вызов передаётся `sshConfirmation: "Разрешаю SSH для этой операции"`; прежнее разрешение на другую операцию не подходит. Предпочитайте настроенные HTTPS remote, если SSH не разрешён.

## Проверка пакета

```sh
npm run check
npm test
```

`check` проверяет манифесты, ссылки пакета, навыки и синтаксис JavaScript. Тесты используют временные Git-репозитории и имитацию HTTP API. Они не создают DerivedData и не обращаются к настоящим проектам. Отдельно доступен `npm run validate` для структуры пакета.

Автоматическая локальная проверка не подтверждает установку в конкретную сессию Codex, доступ к реальным серверам или успешную публикацию УЗС/КЗС. Эти действия проверяются отдельно после настройки; при создании пакета реальные запросы в Jira/GitLab и сборки приложения не выполняются.
